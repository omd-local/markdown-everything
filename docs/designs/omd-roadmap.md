# CEO Plan: omd product roadmap (Hybrid B+A)

Generated by /plan-ceo-review on 2026-05-10
Branch: feat/progress-bar | Mode: SELECTIVE EXPANSION
Repo: omd-local/markdown-everything

## Vision

### 10x Check
omd today is a CLI dispatcher with 0 stars, 0 paying users. The 10x version
combines: paid Mac GUI app (Stage 2) that solves the worst friction in the
space (xhs/Douyin cookie capture via embedded WebView) + canonical MCP
server for content extraction in Claude Code / Codex / Obsidian. The
"paste anything, get Markdown" pain isn't owned by anyone — markitdown
can't do reels, marker-pdf can't do URLs, Reader can't do local files.

### Premise
- **Right problem:** Yes — the dispatch layer is the unique value, not any
  one converter. Confirmed by Layer 1/2/3 landscape: every competitor
  specialises per-format and misses the "paste anything" pain.
- **Framing undersold:** README sells "Markdown converter." MCP angle
  (agent eyes for any URL) and Obsidian angle (knowledge ingestion pipe)
  would unlock 10× the audience. Roadmap leans into MCP positioning over
  time (CP-2 Obsidian target post-v1.2).

### Eureka (logged)
omd's moat is dispatcher + Chinese-content-first + Apple Silicon local;
competitors specialise per-format and miss the "paste anything" pain.

## Approach
**Hybrid B+A** — Stage 2 GUI app (paid) as headline initiative; new
backends and existing-issue PRs continue in parallel. CLI stays MIT free
+ Homebrew-installable; app is the closed-source / paid layer.

(Throughout this doc: "CC" = Claude Code, the AI assistant compressing
human implementation time ~10×. Effort estimates show both scales.)

## Success / kill criteria for Stage 2 v1
- **Success:** ≥50 paying users at $19 within 60 days of launch (Gumroad
  count). At least one positive write-up on r/macapps or HN.
- **Partial success:** 20-49 paying users → keep going, iterate on UX.
- **Kill criteria:** <20 paying users in 60 days AND <10% CLI→app
  conversion → mothball the paid app, refund all sales, double down on
  free CLI + MCP positioning (Approach C path).
- **Conversion measurement (N1):** add an opt-in install ping to the
  CLI's first run (separate consent from app telemetry). Endpoint
  records `{anonymous_uuid, install_date, app_version, source=brew}`.
  Definition of conversion: `Gumroad sales in 60d / CLI installs in 60d`.
  Without this metric the kill criterion is unmeasurable.

## CLI-user upgrade path (N2)
- Existing Homebrew CLI users with install age >30 days get **$5 off**
  via discount code shipped through `omd --upgrade-info` (added to CLI
  in a 1h patch alongside install ping).
- Discount code redeemable on Gumroad listing.
- Recognises that CLI users are the highest-converting cohort and
  rewards early adopters.

## v2 paid-upgrade precedent (N6)
- Stage 2 v1 is $19 one-time, free updates within v1.x line.
- **v2.0 (post-1000 users)** ships as a paid upgrade at $9 for existing
  licences (50% off new-user $19). This is set now to avoid feeling
  locked into "free updates forever" later. Communicated clearly on
  Gumroad listing: "v1 buyers get all v1.x updates free; v2.0 is a
  separate paid upgrade for sustained development."

## Pricing
- **$19 one-time** purchase via Gumroad. No subscription.
- **14-day refund** window (Gumroad default).
- **No trial** in v1. (CLI is the trial — anyone can `brew install` and try
  the conversion engine before deciding the GUI is worth paying for.)

## CLI ↔ app version contract
- Stage 2 .app **bundles `omd` CLI exclusively**. App ignores any
  brew-installed `omd` on `$PATH` to avoid version drift bugs.
- App's bundled CLI version is recorded in `Resources/omd-version.txt`.
- Updates to the bundled CLI ship via app update (Sparkle in v1.1) — never
  via brew. App users who also use the CLI run them as separate worlds.

## Stage 2 v1 — minimum set (CONFIRMED)

> **Day-1 spikes (before committing to estimates below):**
> - **Spike A:** Tauri spawns bundled `omd --version` end-to-end on a
>   notarized DMG. If Python runtime + mlx + whisper deps fail to bundle
>   cleanly, fall back to PyInstaller-built single binary first.
> - **Spike B:** WebView cookie extraction on xhs.com — capture cookies
>   from a successful login, write Netscape cookies.txt, run `omd <xhs-url>
>   --cookies <file>` end-to-end. If Tauri's WebView API doesn't expose
>   cookies cleanly, evaluate `webkit2gtk` / native WKWebView bridge.
> Both spikes complete before Day 4 of the calendar — they de-risk the
> two highest-uncertainty items.

1. **Tauri scaffold + Svelte UI** (commit to Svelte: smaller bundle,
   Tauri-default ergonomics; React adds bundle bloat solo dev doesn't need)
   — human ~1 week / CC ~2 days
2. Drag-and-drop file or paste-URL → bundled `omd` CLI subprocess
   — human ~2 days / CC ~4h
3. **WebView cookie capture** for `xiaohongshu.com` + `douyin.com`
   — human ~5-6 days / CC ~1.5 days (revised up from 3-4 per Spike B
   risk; this is the moat — no competitor solves cookie UX)
4. Save dialog → write `.md` — human ~1 day / CC ~2h
5. Bundle `omd` CLI inside .app (Python runtime + mlx + whisper), sign +
   notarize, produce DMG — human ~5-6 days / CC ~1.5 days (revised up
   from 2; first-time Apple Developer setup + Python bundling friction +
   notarization first-bounce iteration)
6. Gumroad listing + license-key check — human ~1.5 days / CC ~4h
   - **License model:** Gumroad license key entered on first launch.
   - **Online check:** on first launch + once every 30 days.
   - **Offline grace:** 7 days. After grace, app shows "verify licence"
     modal but keeps working in read-only mode (lets users export their
     existing conversions).
   - **Refunds:** Gumroad webhook → invalidates licence on refund. Next
     online check fails → app reverts to read-only.
7. **CP-4 ACCEPTED:** Anonymous opt-in telemetry on first launch
   - **Privacy posture:** opt-in only (default off). Single first-launch
     question with both options labelled clearly: "Help me improve omd?
     [Yes — share usage data] [No — keep it private]".
   - **Data collected:** backend type used (e.g. "podcast"), conversion
     duration, success/fail, app version, macOS version. **NEVER** URLs,
     filenames, content, or anything user-identifying.
   - **Device ID:** random UUID v4 written to
     `~/Library/Application Support/omd/telemetry-id`. Regenerated on
     reinstall. Resettable from settings.
   - **Endpoint:** Cloudflare Worker → Tinybird free tier (committed —
     not DuckDB optionality; solo dev picks one and ships).
   - Effort: human ~1 day / CC ~3h.

**Revised total:** human ~5-6 weeks / CC compresses to ~1.5 weeks.
(Original ~3 weeks underprice, per spec review — notarization first-time
+ Python bundling + WebView cookie extraction are non-trivial.)

### If Spike A (Python bundling) fails (N8)
Step 5 changes shape:
- Ship a **PyInstaller single-binary** of `omd` instead of bundling the
  full Python runtime. Smaller, easier to notarize, but loses in-app
  control over which Python version / mlx version is active.
- Document in app's About panel: "GPU-accelerated transcription requires
  the brew CLI version of `omd` (run `brew install omd-local/omd/omd`).
  This bundled version uses CPU whisper which is slower for long audio."
- Update step 5 estimate down by ~2 days (PyInstaller is simpler).
- App still ships in Week 3, but with reduced transcription performance.

## Risks
- **Solo-dev calendar:** Stage 2 v1 + parallel backends is wide front.
  Discipline: no new backends until #3, #1 land. No CP-1/2/3 until v1 ships.
- **Notarization first-time pain:** Apple Developer account ($99/yr) +
  provisioning + entitlements. Budget +2-3 days for first-time setup
  including hardened-runtime entitlements + Tauri-specific notarization
  quirks (already reflected in step 5 estimate).
- **Python bundling inside Tauri .app:** Non-trivial. mlx + whisper deps
  are large + Apple-Silicon-specific. PyInstaller / py2app fallback if
  Tauri scaffold can't bundle directly. Spike A on Day 1 de-risks.
- **Cookie WebView UX:** xhs and Douyin both ship anti-bot detection.
  Tauri's WebView API is thinner than Electron's; cookie extraction may
  need custom WKWebView bridge. Spike B on Day 1 de-risks. Test that
  captured cookies survive a real conversion before declaring v1 done.
- **Cookie capture legal / ToS exposure:** xhs + Douyin ToS both forbid
  automated access. Capturing user-driven WebView cookies for use on
  user's own behalf sits in a grey zone — defensible (user logs in
  themselves; no scraping at scale; no credential reuse) but not free of
  risk. Mitigation: in-app disclosure on first cookie capture
  ("This logs you into your own xhs account; cookies stay on your Mac
  and are used only when you ask omd to convert an xhs note. omd does
  not store, share, or transmit them."). Add a Terms link in the app
  footer pointing to a clear use-policy page.
- **Gumroad / payments:** licence-key check is the simplest model;
  refunds via Gumroad UI. If you outgrow Gumroad's split, migrate to
  Lemon Squeezy. Risk: Gumroad webhook outage → app shows
  read-only-mode false-positive. Mitigation: 7-day offline grace + retry.
- **Telemetry privacy:** must be honestly opt-in; failure here = HN
  flames. Use the pattern in `~/.claude/skills/gstack/bin/gstack-config`
  (gstack itself does this well: separate "anonymous" and "off" modes).
- **Telemetry-as-YAGNI risk (acknowledged):** for first 50 users you
  could read feedback by hand from Gumroad email. CP-4 was kept in v1
  because the user explicitly accepted it (D7) — the value is *roadmap
  signal beyond 50 users*. v1 should also include a
  "feedback@omd.app" mailto link in the About panel as a low-tech
  parallel feedback channel. ~30 minutes to add.
- **No-Sparkle update UX (N4):** v1 ships without auto-update; bundled
  Python+mlx+whisper makes the .dmg ~150-300 MB. Manual re-download is
  brutal. Mitigation: (a) Gumroad listing copy explicitly states
  "v1 updates require manual DMG re-download; auto-update lands in
  v1.1." (b) On every paid sale, capture the email and run a "v1.1
  shipped — re-download here" email blast. (c) Pull Sparkle into v1
  ONLY if Spike A and B both come in under estimate AND there's
  remaining calendar.
- **Apple Developer cert revocation risk (N5):** DMG distribution
  outside App Store dodges App Review, but Apple Developer Program ToS
  still applies. If Apple revokes the cert (e.g., complaint about
  scraping aids), the .app stops launching. Mitigation: keep CLI as MIT
  escape hatch — users can always `brew install` and run the CLI;
  document `xattr -d com.apple.quarantine` sideload instructions on the
  support page so unsigned-but-valid builds remain usable.

## Outside Voice Amendments (eng review, 2026-05-10)

The eng review's outside voice (codex with web search) caught structural
issues the CEO+spec-review didn't surface. User accepted four amendments
that materially change the roadmap:

### Amendment OV-1 — Toolchain bundling reality
Original CEO plan said "bundle Python + mlx + whisper." That undersells.
The CLI is a dispatcher over `markitdown`, `yt-dlp`, `ffmpeg`,
`mlx_whisper`, `tesseract`, `f2`, optional `ollama` — every one needs a
packaging path, codesigning, and notarization entitlements. PyInstaller
fallback (Spike-A) does NOT solve this; it just changes the binary
shape.

**Change:** v1 scope reduced (see OV-3) to drop tools that aren't on the
critical path for v1 surfaces. v1 bundles only `ffmpeg` + `mlx_whisper`
+ `markitdown` + Python runtime. DMG ~150MB instead of 300MB+.

### Amendment OV-2 — Architecture pivot to SwiftUI + WKWebView
Original plan: Tauri 2.x + Svelte 5. Codex argued Tauri buys
cross-platform optionality not needed for a Mac-only paid app while
costing extra stacks to debug + sign. WKWebView native cookie-jar
access is the tool's natural surface for the moat (when re-introduced
in v1.5).

**Change:** Stage 2 v1 ships as **native SwiftUI + WKWebView + `Process`**.
Mac-locked. Cross-platform path is post-v2 community PR territory.

**Decisions made obsolete:**
- D7 (Rust → JS error serde) — MOOT, replaced by Swift error enum
- D10 (Svelte 5 runes / app store) — MOOT, replaced by SwiftUI ObservableObject

**Decisions that survive (pattern, different impl):**
- D2 (subprocess kill on quit) — `Process.terminate()` in SwiftUI
- D3 (stderr ring buffer) — same concept, Swift implementation
- D4 (cookie atomic write) — same Foundation FileManager pattern
- D6 (24h offline grace) — same logic, Swift Keychain instead of file
- D8 (`--json-events` CLI flag) — STILL REQUIRED, Swift parses too
- D9 (cookie-name detection) — same logic, WKHTTPCookieStore API
- D11 (100% test coverage) — XCTest replaces Vitest/cargo test
- D12 (persistent subprocess in v1.1) — same logic

### Amendment OV-3 — v1 scope: stable surfaces only (Hybrid pricing)
Original plan: v1 includes WebView cookie capture for xhs/Douyin (the
moat). Codex argued: shipping the most-failure-prone surface in v1 risks
schedule + reputation; let packaging prove itself first.

**Change:** v1 ships GUI for STABLE surfaces only — docs (markitdown),
web URLs, YouTube/Apple Podcasts, image OCR (tesseract STILL needed —
revising OV-1: bundle tesseract + Chinese language pack). xhs/Douyin
capability ships as **v1.5** paid unlock.

**Pricing change:** two-tier release.
- **v1.0** at **$9 one-time** — stable surfaces (docs, web, YouTube,
  Apple Podcasts, OCR).
- **v1.5** at **$10 upgrade** for v1.0 buyers, $19 for new buyers —
  adds xhs/Douyin via WKWebView cookie capture.
- This lets buyers self-select moat-importance; smaller initial price
  per buyer; reduces v1 risk; revenue from Week 4.

**v1 calendar revised:** ~4 weeks (was 6) thanks to scope cut. v1.5
adds 2-3 weeks once v1 ships and packaging is proven.

**Toolchain bundle for v1:** ffmpeg + mlx_whisper + tesseract +
tesseract-lang (chi_sim+eng) + markitdown + Python runtime + yt-dlp
(for YouTube). Skip f2 (Douyin), skip ollama default (polish remains
opt-in via brew CLI for v1).

### Amendment OV-4 — Telemetry simplification
Original plan: HMAC-signed Worker → Cloudflare Queues → consumer Worker
→ R2 hourly JSON files (D5). Codex called this "infra cosplay for a
$19 desktop app."

**Change:** drop the Worker/Queues/R2 stack. Use **Sentry custom events
+ Cloudflare Worker logs** (already in scope for crash reports per CEO
S8-O1 — single consent prompt, single vendor). Worker accepts HMAC-
signed events, forwards to Sentry, Worker's own logs queryable via
Cloudflare dashboard. Effort: ~2h instead of ~5h.

**Decisions made obsolete:**
- D5 (R2 hourly batches via CF Queues) — REVERSED

### Amendment OV-5 — Licence/clock-skew first-launch fix
Codex flagged: "24h offline grace on first launch" (D6) conflicts with
"server-time clock-skew check" (CEO S2-E2) — no server contact yet on
first-launch grace path.

**Change:** clock-skew check only runs on FIRST online verify (which
happens within 24h grace if network arrives, or immediately if network
is up at first launch). Until first online verify, no skew check is
possible — accept this. Document in licence module.

### Calendar revision (OV-3 + OV-1)
| Phase | Original | Revised |
|-------|----------|---------|
| Stage 2 v1 (stable surfaces) | 6 weeks | **4 weeks** |
| Stage 2 v1.5 (xhs/Douyin moat) | n/a | **+2-3 weeks** |

## Reviewer Concerns (iteration-3, minor — not blockers)
1. **CLI install-ping consent ambiguity:** N1 install ping is opt-in but
   the CLI has no existing consent flow. First-run prompt on patched
   CLI is a behaviour change for existing brew users. Mitigation:
   prompt on first run of patched version, support `--no-ping` flag and
   `OMD_NO_TELEMETRY=1` env var. Add to issue when filing the ping
   work.
2. **Discount-code abuse:** $5-off code via `omd --upgrade-info` has no
   per-user gating; could leak to Reddit. Open question: per-install
   server-side codes (more work, ~half-day) vs accept leak as marketing
   cost. Decide when implementing.
3. **Tinybird free-tier ceiling unstated:** at ~50 users + Worker proxy
   we're fine. Migration trigger: when monthly events exceed Tinybird
   free-tier row cap (currently ~10M rows/month). Revisit then.
4. **Soft-launch / kill-criterion clock:** explicit clarification — the
   60-day kill clock starts at **public launch** (Week 5+), NOT the
   Week-4 soft launch to friends. Don't kill v1.x prematurely from
   soft-launch days counting against the 60.

## Open question (acknowledged, deferred)
**Free v0.9 (no payments) → paid v1.0 split (iter-1 #13):** spec
reviewer suggested a TestFlight-style free pre-release to de-risk cookie
UX before payments add support burden. Counter: the 6-step minimum
already includes Gumroad in v1, and splitting adds calendar without
clear upside (v1 can be soft-launched to 5-10 friends as the de-risk
cohort, with refund-on-bug as the safety valve). **Decision: ship v1
with payments; soft-launch to friends in Week 4 of the calendar above
before public launch.** If WebView cookie extraction proves substantially
flakier than expected during Week 2, revisit and consider a free-first
release.
